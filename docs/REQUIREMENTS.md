# 业务需求与边界

## 1. 范围

实现可演示的 UniApp H5 + Spring Boot 单体习惯打卡应用。所有已实现核心功能必须真实调用后端并真实使用 MySQL/Redis；不得用 Mock 数据伪造已经完成的核心业务。

| 编号 | 必须功能 | 验收标准 |
| --- | --- | --- |
| R1 | 用户登录 | 账户密码验证成功后在 Redis 建立会话，受保护接口可识别当前用户 |
| R1a | 当前用户 | 从服务端会话识别身份，查询并返回安全的用户信息，不含密码哈希 |
| R1b | 用户登出 | 删除当前令牌对应的 Redis 会话，后续请求不能继续使用该令牌，其他会话不受影响 |
| R2 | 创建打卡项 | 名称与描述写入 MySQL，所属用户来自服务端会话 |
| R3 | 查看打卡项 | 只返回当前用户数据；空列表是正常结果 |
| R4 | 每日打卡 | 只对自己的习惯打卡；同用户、同习惯、同业务日期最多一条记录 |
| R5 | 今日状态 | 根据后端业务日期返回已打卡/未打卡；业务缓存 Miss 时回源 MySQL |
| R6 | 当前连续天数 | 根据真实日期计算，今天未打卡、断签、跨月和跨年均正确 |

用户注册为可选加分项，在 Phase 1–11 主线全部完成后最后考虑，不属于主线必做功能或交付验收前置条件，当前未实现，范围及待定决策见 IMPLEMENTATION_PLAN.md 第 6 节。注册应创建真实 MySQL 用户，并可通过现有登录接口认证；同名并发由数据库唯一约束兜底。

当前范围不包含找回密码、修改/删除习惯、补签、撤销、历史日历、排行榜、多时区用户或提醒。

登录演示使用手工执行的独立 demo-data.sql，只写入 BCrypt 哈希；README 标注公开演示凭证，不用于生产。应用启动不创建账户，注册仅在主线全部完成后按单独授权作为加分项实现。

## 2. 已确认的产品决策

本期固定以下规则：

- 统一业务时区：`Asia/Shanghai`。
- 今天尚未打卡但昨天有打卡记录时，当前连续天数保留到昨天，不立即清零。
- 每日打卡为幂等操作：重复打卡作为成功处理，当前返回原记录，不提供 created 标记。
- 当前阶段不做注册功能，使用独立 SQL 准备演示账户；注册留到主线全部完成后最后作为可选加分项，单独设计和验收。
- 不同用户允许创建同名习惯；同一用户内习惯名称必须唯一，由数据库联合唯一约束兜底。
- Redis Session 默认 TTL 为 7200 秒，不滑动续期。
- 今日状态与连续天数使用短 TTL 业务缓存，默认 30 秒；MySQL 始终是最终业务事实来源。

## 3. 输入及数据边界

以下是验收要求。当前认证模块已补齐用户名与密码边界、字符串 ID 和已删除用户会话清理；真实 MySQL/Redis 联调仍待验收。Habit 创建、去重和分页已实现；打卡提交已实现，今日状态及连续天数仍为后续范围。Habit 已落实下述 Unicode 码点、字符串 ID 等接口规则。

- 用户名：3–32 位 ASCII 字母、数字或下划线；trim 后统一转小写用于查询和唯一性判断。
- 密码：需非空白且8–72 个 UTF-8 字节，不 trim；使用 BCrypt 安全哈希存储。
- 习惯名称：trim 后 1–50 个 Unicode 码点。
- 描述：可选，最多 200 个 Unicode 码点；空描述统一存 `NULL`。
- ID：正整数；API 中按十进制字符串传输 BIGINT，避免 H5/JavaScript 大整数精度问题。
- 客户端不得指定 `userId`、`checkinDate`、`streakDays` 等服务端字段。
- 创建习惯本期不提供业务幂等保证；前端提交期间禁用按钮仅用于体验优化。
- 每日打卡单独提供幂等保证。

Habit 创建返回 HTTP 201，列表返回 200；响应 ID 为字符串、时间为带 Z 的 UTC 时间点。名称先 trim 再校验码点长度；描述先校验最多 200 码点，空字符串及纯空白统一为 NULL，有内容的描述保留原文。仅指定名称唯一约束冲突归为 40901，未知唯一键冲突不当作业务重名。

## 4. 业务时间

全局业务时区为 `Asia/Shanghai`。后端在业务操作开始时捕获同一个时间点并计算业务日期 D，后续 SQL、缓存 Key 和响应均使用该 D。

UTC 时间戳与业务日期分开保存：

- `checkin_date`：业务时区的自然日。
- `created_at`、`checked_in_at` 等：UTC 时间戳。

系统默认时区、浏览器时区或客户端时钟不能改变打卡日期。

午夜前已经进入业务处理的请求仍归属于其捕获的日期 D；午夜后的新请求属于新业务日期。跨午夜重试可能分别形成两天各一条合法记录，本期不做跨日期请求去重。

不支持补签和未来日期。业务时区属于数据语义，一旦已有业务数据，不得只通过修改配置直接改变历史含义。

## 5. 当前连续打卡天数的准确语义

针对一个用户的一个习惯，以业务日期 D 为准：

1. 如果 D 有记录，从 D 开始向前逐日计数。
2. 如果 D 没有记录、D−1 有记录，从 D−1 开始计数；今天尚未结束，不立即清零。
3. 如果 D 和 D−1 都没有记录，当前连续天数为 0，即使更早存在历史连续记录。
4. 从锚点每次向前一个自然日，遇到第一个缺失日期立即停止。
5. 当前连续天数不是最大历史连续天数，也不是总打卡次数。

| D | 实际打卡日期 | checkedIn | streakDays | streakEndDate |
| --- | --- | --- | --- | --- |
| 2026-09-17 | 无 | false | 0 | null |
| 2026-09-17 | 09-15、09-16、09-17 | true | 3 | 2026-09-17 |
| 2026-09-17 | 09-15、09-16 | false | 2 | 2026-09-16 |
| 2026-09-17 | 09-14、09-15 | false | 0 | null |
| 2026-09-17 | 09-14、09-15、09-17 | true | 1 | 2026-09-17 |
| 2026-03-01 | 02-28、03-01 | true | 2 | 2026-03-01 |
| 2027-01-01 | 2026-12-31、2027-01-01 | true | 2 | 2027-01-01 |

实现时后端读取日期不晚于 D 的打卡记录，按日期倒序并使用 `LocalDate` 逐日比较。不能简单用记录总数，也不能只固定查询最近 N 天而截断真实连续记录。

## 6. 幂等、并发、权限与异常

数据库约束：

```text
UNIQUE(user_id, habit_id, checkin_date)
```

是每日打卡的最终并发防线。

每日打卡接口采用：

```http
POST /api/v1/habits/{habitId}/checkins
```

首次和重复请求都返回 HTTP 200、`code=0`：

- 首次成功：返回新记录的 id、habitId、checkinDate、checkedInAt。
- 同一业务日期重复请求：返回原记录，不提供首次/重复标记。
- 重复请求返回已有记录的 `id` 和原始 `checkedInAt`。
- 无论快速重复点击、浏览器重复提交、网络重试或并发请求，数据库最终都只能存在一条记录。

只允许将指定打卡唯一约束冲突识别为重复打卡。死锁、连接失败、外键异常等不能伪装为重复成功。

错误分类必须来自明确业务原因或异常类型，不能从 HTTP 状态反推。相同 HTTP 状态允许多个业务码；无法判断原因时统一返回 HTTP 500 / 50001。客户端不接收内部异常原文，日志也不得包含密码或完整 Token。

所有查询和写入都必须从 Redis Session 获取用户身份：

- 前端不得传 `userId` 代替登录身份。
- 用户只能访问自己的打卡项和打卡记录。
- 他人资源与不存在资源统一返回 404。
- 用户不存在与密码错误对外统一为登录失败。
- 已有 Session 指向不存在用户时，应清理该会话并返回 401。

## 7. Redis 使用边界

Redis 必须真实参与业务，但不承担核心数据持久化。

- 登录态：Redis Session。
- 今日打卡状态：短 TTL 缓存。
- 连续天数：短 TTL 缓存。
- 业务缓存 Miss 时回源 MySQL。
- MySQL 打卡事务提交成功后删除相关 `today` / `streak` 缓存。
- 缓存删除失败时记录日志并依赖短 TTL 收敛，不回滚已经成功的 MySQL 事务。
- 已完成鉴权后，如果仅业务缓存访问失败，可直接查询 MySQL。
- Redis Session 无法校验时不得绕过登录认证。

本期不为缓存引入分布式锁、跨存储事务或复杂并发回填协议。
